# Verification record: a parent prints today's pack as a PDF

Feature: a parent opens `/today/`, taps **Print**, picks a sheet, and prints a
clean US Letter PDF. This is the critical path of the public pack, so it is
checked on every pull request and every push to `main`.

- Check: `tests/print-browser.mjs` (`npm run verify:print`; also the first step
  of `npm run test:browser`, which the `check` job in
  `.github/workflows/check.yml` runs).
- Agent skill and feature map: `.cursor/skills/verify-wonder-daily-print/`.
- Evidence a run leaves behind: `output/print-verify/` (sample PDFs, one PNG
  per printed page, menu screenshots, `summary.json`). Not committed: it is
  rebuilt from the day on `/today/`, so it changes every morning. The folder must
  be outside `dist/`, and new, empty, or made by this script before; the script
  removes only the files its earlier run created and listed in the folder's
  `.print-verify` marker. If the folder holds any other file, the run stops before
  it writes, removes or records anything, so a file it did not create is never
  overwritten or deleted.

## What the check does

It builds nothing itself; CI runs `npm run archive` first, then serves `dist/`
on a random local port and drives Chromium and poppler. It stops at once with a
clear message if `pdfinfo`, `pdftotext`, `pdftoppm` or `pdfimages` is missing
(`poppler-utils`; `family.test.mjs` already needs it in CI).

## Proof that it can fail

Each of these was applied to a copy of `dist/` and the check went red:
a PDF replaced by a blank page ("looks blank"), a PDF deleted (404), a see-through or covered menu, a swallowed click on a Print menu entry (Math, not only Print today), a lab page declared with empty materials, a "Page 8" age footer, a see-through trigger background, a link
pointing off the site or at another folder, a renamed menu label, "Print today"
made of Math twice ("sheet 3 is not foldable"), a stale sheet from an earlier day
inside Print today, an answer key or lab sheet swapped for another PDF, a lab PDF whose menu link was removed, the pack
age changed (header no longer says it), the Print menu markup removed, the
Escape handler removed, the welcome art deleted ("pictures not loaded for
print"), "Age 8" changed to "Ages 6-8" on the page, and a name added to
`WD_PRIVATE_NAMES` that appears in the PDFs.

## Tomorrow's pack

Content checks read `pack.json` and the PDFs, never fixed text. As a trial, each
earlier day under `dist/days/` was copied over `dist/today/` and the check run.
Four pass (2026-10-21, -22, -23 and -28). The rest carry older page templates:
seven predate the `targetAge` field and fifteen hide the grown-ups footer in
their own CSS, so they stop first at the visible-age check. Before that check
was tightened, 19 of 26 passed every other step, so print layout and PDFs are
stable across templates; the visible footer is what depends on the current
page template. A generator change that hides it again fails this check on
purpose.

## When it fails

1. Run `npm run archive && npm run verify:print` locally.
2. Open the PNGs in `output/print-verify/` for the sheet named in the error.
3. If the layout change is intended (for example a new sheet in the bundle),
   change the check and this record in the same pull request. Do not loosen an
   assertion to get green.

## Known limitation: the Foldable story has no text layer

The Foldable story PDF is a single image-only sheet (a raster, no text layer), so
`pdftotext` cannot read it. A wrong but well-formed picture there is caught only by
its size, ink, document title, a real full-size picture, and the page-for-page picture
comparison against the Foldable sheet inside Print today. Its copy is not tied back to
`pack.json` by this check. This is a known, documented gap and is out of scope for this check. Two things would close it: OCR on the CI runner (read the raster and compare to
`pack.json`), or a text layer in the foldable generation (so `pdftotext` can read it).
Neither is done in this change.

## Not covered

The Foldable's own picture (see above): its copy is not read back (it has no text layer), so a wrong
but well-formed raster there is caught only by size, ink, title and the page-for-page
comparison inside Print today. Its words come from `pack.json`, which the public privacy
scan already reads. Also not covered:
`/little/` print link (`tests/little-browser.mjs` covers the link), `/family/print/`,
a physical printer, and Safari/Firefox print engines (`page.pdf` is Chromium only).
